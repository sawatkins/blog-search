# Runtime and dependency audit — 2026-09-07

## Result

Applied the five-second per-host request default, upgraded the live app to Python
3.14.7, patched its dependencies, and patched Elasticsearch/Kibana to 9.3.8.
The web service is active and uses the new interpreter. Crawler/source timers
remain uninstalled/inactive. No full crawl, source sync, reindex or schema change
was performed. Frontend design and unrelated services were not changed.

**Final verification:** 219 tests passed in 8.612 seconds on the deployed Python
environment. All 45 installed runtime packages pass compatibility checks and the
known-vulnerability scan. PostgreSQL and Elasticsearch each retain 314,974 pages;
the crawler has 931 jobs and no pending index updates.

## Docker/build findings

The previous `COPY . /app` had no `.dockerignore`, so a build could copy local
`.env` files, backups, virtual environments and git metadata. There is no evidence
from this audit that a secret-bearing image was previously published; this is a
confirmed build configuration hazard, not a claimed credential leak.

The build now allowlists inputs, explicitly copies only app source, uses a
digest-pinned Python 3.14.7/Debian 13 image and pinned uv, runs as UID 10001 instead
of root, and starts Uvicorn directly without resolving/installing packages at
container startup. The first attempt to use uv's public GHCR image was denied by
the registry; installing the exact uv wheel from PyPI built successfully instead.

Built `blogsearch:runtime-audit-20260907` (image ID
`sha256:20a96ea15dce9f2d5bc7db0907fdcf47a44c74c0560a843606699d02cb5f7f86`).
Network-disabled container tests verified imports, article extraction, five-second
default, non-root cache writes and web lifespan handling. The image contains no
`.env`, backup directory or git metadata. Refreshed APT metadata in a disposable
copy of the image reported zero available package upgrades. The live app remains
a systemd service; building this image did not move production into Docker.

## Search-service patches and backup

Elasticsearch and Kibana were both 9.3.2. Vendor release notes identify security
fixes in 9.3.8, so both were updated within the same minor series. Their images
are pinned by version and digest. Both HTTP ports remain bound to localhost.
Elasticsearch retains its existing 8 GB heap, 12 GB memory limit and data volume
`elastisearch_esdata`; Kibana retains its 2 GB limit. No new search engine or broker.

The managed Compose definition is [elasticsearch.compose.yml](../elasticsearch.compose.yml).
Its live copy is `/home/debian/docker-compose/elastisearch/docker-compose.yml`.

Before patching, added a local snapshot repository and took the snapshot:

- Repository: `blogsearch_local`
- Snapshot: `before-runtime-audit-20260907`
- Location: `/home/debian/blog-search/backup/elasticsearch-snapshots`
- Result: **SUCCESS, all 43 shards**, including cluster state; approximately 2.1 GB.

Restored that snapshot into a separate 9.3.8 container with temporary data storage
and read-only repository access. All 43 primaries became available and the restored
`pages` count matched production at 314,974. The complete 219-test suite also passed
against this patched test server before changing the live containers.

After patching, Elasticsearch has the same document count and Kibana reports
`available`. Elasticsearch's existing yellow status is unchanged: one replica is
unassigned on this single-node installation. There are no unavailable primaries.
The snapshot is local upgrade recovery, not an off-machine disaster-recovery backup.

## Host findings and deliberately pending work

Refreshed host APT metadata and simulated an upgrade: **zero pending package
upgrades**. Docker Engine is 29.8.0 and containerd is 2.3.4. Debian 12 is in LTS;
this pass did not perform a whole-OS migration or restart shared Docker services.
Plausible, its databases, Watchtower and other unrelated services were left alone.
Neon is managed externally; its PostgreSQL server was not upgraded by this task.

**A host reboot is still needed:** kernel 6.12.95 is installed, but the running
kernel is 6.12.73 and `/var/run/reboot-required` exists. That predates this audit.
A reboot affects unrelated applications, so it requires the user's maintenance
decision. Updating Python and the app containers does not activate the new kernel.

This was a runtime/dependency/update audit, not a full review of OS hardening,
firewall rules, reverse-proxy configuration, application authorization or backup
retention. Package scans and patch checks are not equivalent to those reviews.

## Recovery and handoff

Preserved prior project metadata, Compose configuration and the previous live
Python 3.10 environment under:
`/home/debian/blog-search/backup/runtime-audit.zmCA3C/`.

For an app-only rollback: stop `blogsearch.service`, move the new `.venv` aside,
move `venv-python310` from that backup back to the original `.venv` path, and start
the service. Console-script paths are only valid after restoring that original
location. Restoring the backed-up dependency metadata is also needed before using
`uv sync` for the old environment. The upgraded search server supports the old
8.x client for recovery.

**Do not downgrade an Elasticsearch image against the upgraded data volume.**
Search rollback requires restoring the pre-upgrade snapshot into a fresh compatible
cluster/data volume. Keep the old snapshot and original configuration intact.

and the earlier backend reliability changes. Live `/`, `/latest`, `/bot`, `/about`
and read-only `/api/search` checks succeeded. Test search requests used the API,
which does not write query analytics. Temporary test services were stopped; no
test database or restore-test Elasticsearch remains running.
